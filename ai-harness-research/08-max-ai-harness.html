Este diagrama reconstruye el flujo real de tu framework a partir del código en max_ai/. El foco es qué función llama a cuál cuando el usuario escribe en el chat.

Core runtime

max_ai/base/agent.py owns preparation, compaction, checkpointing and public run APIs.

Reasoning

max_ai/reasoning/react_self_directed.py owns the ReAct loop, guards, plan tools, retries and stopping.

Execution

ToolExecutor resolves, validates, approves and dispatches tools to local or sandbox executors.

Web entry

max_ai/ui/server.py converts chat requests and runtime events into SSE events for the UI.

1. Chat entry: from Enter to the harness

VERIFIED The web layer does not call the model directly. It creates a request, selects a context, starts the Agent engine, and translates typed events into SSE.

2. The actual turn pipeline

Your Agent prepares infrastructure once per run, while the client assembles the provider-neutral prompt and transforms it to OpenAI or Ollama format on every model call.

3. Tool call: from model to environment

Built-in surfaces VERIFIED

BashTool, WorkspaceTool, function tools, plan/update_plan, ask_user, scratchpad, knowledge/context tools and skill runtime tools. Aggregation occurs in AgentCapabilities.

Security boundary VERIFIED

CoreRuntimeTool routes to a sandbox executor. Bash has pattern blocks, but the code says those patterns are not the containment boundary; Docker is the primary boundary.

Middleware boundary VERIFIED

Middleware wraps the side-effecting execution step, not resolution, approval or schema validation. Policy that must see raw arguments needs a dedicated pre-dispatch hook.

4. State, pause, resume and output

VERIFIED Approval and ask-user are durable record states. The stream ends with finish_reason=approval_needed or input_needed; the UI applies the decision/answer and resumes the same context.

5. Best-practice review

Strong foundations

Typed messages; provider adapters; JSON Schema validation; explicit tool lifecycle; cancellation; bounded parallelism; local/Docker split; compaction; checkpoint hooks; structured events; resumable approvals; deduplication; prompt layers; memory/logbook separation.

Priority 1 · concurrency

VERIFIED app.state.turn_lock is global. It serializes unrelated users, sessions and agents. Prefer a keyed lock by (user_id, session_id, agent_name), plus a distributed lock for multiple workers.

Priority 2 · durable sessions

VERIFIED UI sessions live in app.state.sessions; Agent storage is optional and checkpoint failures are best-effort. Production should use an authoritative, versioned, atomic session store with recovery states.

Priority 3 · verifier contract

INFERRED GAP Tests/builds can run through Bash, but there is no first-class verifier result distinguishing “model finished” from “acceptance checks passed”. Add verifier plugins with structured checks, timeouts and evidence.

Priority 4 · policy before execution

VERIFIED Approval and validation happen before middleware, while middleware wraps execution. Add a policy/interceptor stage receiving every call, capability metadata and session identity before approval or execution.

Priority 5 · context provenance

RECOMMENDATION Prompt layers are strong, but expose a per-call context manifest: source, trust level, token count, truncation and compaction status. Treat repository text and tool output as untrusted data.

Priority 6 · durable event log

RECOMMENDATION SSE is transport, not durable observability. Persist immutable run/tool/policy events separately from mutable RunContext so UI state and audits can recover after reconnects.

Priority 7 · retry classes

VERIFIED The framework has loop iterations and connection retries. Make retry classes explicit: API transport, schema correction, tool failure, verifier failure and model continuation.

Recommended target flow

Chat request → session resolver → per-session lock → append user event → context builder + provenance → model adapter → typed model result → tool policy → approval gate → schema validation → middleware → executor/sandbox → structured result → event log + transcript → verifier → context update → next turn → final response with checks and audit id

Conclusión: tu framework ya tiene muchas piezas de un harness serio. El mayor trabajo pendiente es convertir sesión, policy, verificación y observabilidad en contratos de primera clase, y evitar que la UI sea dueña del estado de ejecución.
