OpenAI Agents SDK

Python-first framework for building agent workflows. Unlike a coding CLI, it is a general runtime: the application supplies the workspace tools and policy, while the SDK supplies turn management, tool execution, handoffs, sessions, guardrails, human interruptions and tracing.

VERIFIED: docs + sourceopen sourcePythonResponses API by default

Official repository

openai/openai-agents-python

Model boundary

OpenAI Responses API is the default model transport; model reasoning, streaming and tool-call emission are model/API capabilities. Runner owns orchestration.

Coding relevance

Function tools, local/hosted tools, shell, apply patch, MCP and Sandbox agents can form a coding harness, but the SDK does not prescribe one repository or CLI.

2. Architecture overview

3. Component map

A · Runner loop VERIFIED

Runner calls the LLM, classifies final output, handoff or tool calls, executes tools, appends results and loops. max_turns raises MaxTurnsExceeded; streaming is a separate Runner path.

B/C · Model + context VERIFIED

Agent instructions, input items, session history, handoff filters and call_model_input_filter shape the model input. Sessions persist working context; optional nested handoff history compacts/rewrites history. Context-window management beyond those documented hooks is UNKNOWN.

D/E · Tools / dispatch VERIFIED

Function tools have schemas and validation; hosted tools include web search/file search/code interpreter/image generation; built-ins include computer, shell, apply patch and local shell; MCP exposes remote tools. Runner handles tool calls and tool errors.

G · Guardrails / approval VERIFIED

Input/output guardrails and tool input/output guardrails can tripwire and stop runs. Human-in-the-loop uses interruptions and resumable RunState; approval is a tool/workflow concern, not a universal OS sandbox.

F · Environment VERIFIED

SDK can call application-defined tools and Sandbox agents with isolated workspaces. The OS/container boundary is delegated to the selected tool/sandbox client.

H · Verification VERIFIED

Guardrails are explicit validators. Tests/builds are application tools. The Runner verifies tool/guardrail protocol outcomes, not arbitrary repository correctness.

I · State VERIFIED

Sessions persist working context; RunState enables pause/resume; server-managed conversations may use conversation_id or previous_response_id. External files/git are application state.

J · Subagents VERIFIED

Handoffs transfer control to another Agent; Agents as tools delegate without changing the main agent. They receive configured input/history and return results through the Runner pipeline.

K/M/N · Hooks / tracing / human

VERIFIED Model input filters and lifecycle callbacks shape calls; built-in tracing records runs, agents, tools and handoffs with sensitive-data controls. Interruptions support human feedback and resume.

L · Extensions

VERIFIED Function tools, hosted tools, MCP servers, agents-as-tools, handoffs and sandbox clients are extension seams. Plugins/skills are not a named core primitive in the SDK docs.

4. Runner loop + 5. data flow

Agent + instructions + session history → model adapter → Responses API; output classification → final | handoff | tool; tool call → guardrails/approval → executor; output items → Session/RunState → next Runner turn; spans → tracing backend.

6. Code structure

src/agents/run.py and runner modules

Public Runner lifecycle, run results, streaming and turn control.

src/agents/agent.py

Agent definition: instructions, tools, handoffs, guardrails and model settings.

src/agents/memory / sessions

Session and conversation-state abstractions for persistent working context.

src/agents/tools and MCP

Function tools, hosted/built-in tools and MCP server adapters.

guardrails / interruptions

Tripwire validators and human-in-the-loop pause/resume state.

tracing

Built-in spans and exporters for workflow observability.
