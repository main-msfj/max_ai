Diagnóstico de los tres síntomas reportados: planificación irregular, falta de acceso al proyecto y falta de ejecución de código. Basado en el código local; los diseños futuros se señalan como propuestas.

VERIFIED · PLAN

El plan es opcional

El loop ofrece update_plan. El modelo decide cuándo usarlo. No hay una obligación universal de planificar antes de actuar.

VERIFIED · WORKSPACE

Artefactos ≠ repositorio

WorkspaceTool solo lista y lee el directorio de artefactos del usuario. No es una herramienta de edición del proyecto.

VERIFIED · EXECUTION

Bash depende de skills

El registro añade Bash automáticamente cuando hay skills. Añadir Bash manualmente tampoco activa por sí solo el flag de sandbox.

Flujo actual: dónde se decide la capacidad

1. Configuración de AgentToolset, capabilities, workspace y executor opcionales.
↓
2. AgentCapabilitiesSiempre workspace; Bash nativo solo si hay skills. El requisito de sandbox se calcula desde skills.
↓
3. Binding y entornoRuntime del usuario: tools / skills / artifacts. Local o Docker según la composición.
↓
4. Contexto + modeloEl modelo solo puede llamar a las tools que recibe; decide si utilizar update_plan.
↓
5. ToolExecutorResolver → validar → aprobación → middleware → ejecutor.
↓
6. Resultado → contexto → siguiente llamadaEl loop gestiona continuaciones, pausas, guards y límites.

Conclusión: el siguiente paso es componer un perfil de coding explícito. Cambiar el prompt o exigir un plan no proporciona herramientas que no están registradas ni monta el repositorio dentro del entorno.
