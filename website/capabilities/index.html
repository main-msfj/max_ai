Capabilities

The public Agent composes model, reasoning, tool, execution, and optional context providers. Each provider implements a contract under max_ai.base and ships concrete implementations under max_ai.capabilities.

Workspace and execution#

WorkspaceBase owns persistent user files and skill materialization. ExecutorBase runs executor-routed tools, and EnvironmentManager manages sessions linking the two. The Agent defaults to LocalWorkspace and LocalExecutor; Docker and Modal are alternatives for execution. Local execution runs on the host and is not a sandbox. Workspace and executor are separate providers.

WorkspaceBaseEnvironmentManagerExecutorBase

Remote workspaces

AzureBlobWorkspace and MinIOWorkspace (max_ai.capabilities.workspace) keep a user's files in object storage instead of local disk, so a serverless instance or another server sees the same workspace. The Agent downloads a user's files when a run starts and uploads changes when it ends; only a manifest of file hashes is compared, so unchanged files never move. Scratchpads and materialized skills stay local, since they are throwaway per run.

Object-storage workspace
from max_ai.capabilities.workspace import AzureBlobWorkspace, MinIOWorkspace

workspace = AzureBlobWorkspace(
    "https://myaccount.blob.core.windows.net/workspaces",
    api_key_env="AZURE_STORAGE_KEY",
)
# Or: MinIOWorkspace("http://localhost:9000", bucket="workspaces",
#                     access_key_env="MINIO_ACCESS_KEY", secret_key_env="MINIO_SECRET_KEY")
agent = Agent(..., workspace=workspace)

Needs pip install "maxai[azure-blob]" or "maxai[minio]". MinIO's endpoint also accepts any S3-compatible store, including AWS S3.

Memory#

These are three different ways to add context. Memory is user/session data that can change during a run. A skill is a reusable procedure with instructions and files. Knowledge is a curated collection searched on demand. Enable each by passing its registry to Agent; a configured capability contributes its tools and prompt layer.

Memorypersonal · session scoped↔Agent runRunContext user_id + session_id↔Skillsinstructions · workspace files
Knowledgecurated source · retrieval tool→Model contextlayer text + tool results←SKILL.mdread when the task calls for it

Choose a backend based on where the agent runs: Local for a simple file store, SQLite for a shared local database, or MongoDB for state shared across application servers. Each registry accepts the same user and session scope from the Agent.

Local memory

Receives: base_path is required. You can also set tool_mode, context_days, and an embedding. The Agent binds each run's user_id and session_id.

Stores: A JSON file for each user and session under base_path/memory/. Best for a single process and simple local persistence.

Search: Cross-session memory search defaults to local semantic embeddings. Set embedding=None to use word matching.

Local registry
LocalMemoryRegistry(
    base_path="./agent-data",
    tool_mode=MemoryToolMode.FULL,
    context_days=30,
)
SQLite memory

Receives: Required base_path; optional db_name (default memory.sqlite3), tool_mode, context_days, search_limit, and embedding.

Stores: Memory records and their embeddings in one SQLite file, scoped by user, session, and category. Suitable for one process or a small deployment on one machine.

Search: Semantic search is the default. Passing embedding=None uses text matching instead.

SQLite registry
SQLiteMemoryRegistry(
    base_path="./agent-data",
    db_name="memory.sqlite3",
    search_limit=20,
)
MongoDB memory

Receives: Optional database, collection, uri_env, server_selection_timeout_ms, context_days, search_limit, and embedding. The MongoDB URI is read from the named environment variable.

Stores: User and session records in a shared MongoDB collection, so multiple application servers can use the same store. Install the mongodb extra.

Search: Semantic search is the default. MongoDB Atlas can use vector search; other servers rank candidates in Python. Pass embedding=None for text matching.

MongoDB registry
MongoDBMemoryRegistry(
    uri_env="MONGODB_URI",
    database="max_ai",
    collection="memory",
)

Skills: local procedures#

A local skill source contains one directory per selected skill, each with a SKILL.md. Its YAML frontmatter declares name and description. During preparation the registry validates selected skills and reads their short catalog entries. SkillsLayer gives the model that catalog; when a task matches, the model uses the built-in read_file tool to open the full SKILL.md, then follows its procedure and uses any accompanying scripts or references. Skills are not callable tools: they teach the agent when and how to use tools.

Example skill package and Agent wiring
skills/
└── invoice-review/
    ├── SKILL.md       # YAML name/description + procedure
    ├── references/    # optional detailed guidance
    └── scripts/       # optional helper programs

from max_ai.capabilities.skills.local import LocalSkillRegistry
skills = LocalSkillRegistry(source="./skills", skills=["invoice-review"])
# Pass skills=skills and workspace=LocalWorkspace(...) to Agent.

Preparation stages selected skills in the registry cache. Before a run, the workspace materializes them under its per-user skills/ directory; existing workspace edits are preserved.

Knowledge: retrieval on demand#

A knowledge registry turns a curated document collection into a named search tool. Choose Local, SQLite, or MongoDB for storage; each backend below explains its constructor inputs, ingestion, and search behavior.

capabilities/memorycapabilities/skillscapabilities/knowledgecontext registry exists separately; not an Agent constructor input
Local knowledge

Receives: Required name, description, and base_path; optional tool_mode and embedding. The name determines the search tool, such as search_product_docs.

Stores: Reads blocks from base_path/knowledge/{name}.json. Document ingestion is external to the Agent; prepare the JSON file before searching.

Search: The model supplies a query and optional result limit. The default local embedding ranks matching KnowledgeBlock records by meaning.

Local knowledge source
LocalKnowledgeRegistry(
    name="product_docs",
    description="Search product manuals.",
    base_path="./agent-data",
)
SQLite knowledge

Receives: Required name, description, and base_path; optional db_name, tool_mode, min_score, and embedding.

Stores: Each block's text, metadata, and embedding in SQLite. Use upsert_block(block_id, block) and delete_block(block_id) from application code to manage documents.

Search: The Agent exposes a named search tool. New or changed block text is embedded on write; the query is embedded when searched.

SQLite knowledge source
SQLiteKnowledgeRegistry(
    name="product_docs",
    description="Search product manuals.",
    base_path="./agent-data",
    min_score=0.2,
)
MongoDB knowledge

Receives: Required name and description; optional database, collection, uri_env, server_selection_timeout_ms, tool_mode, min_score, and embedding. The connection URI is read from the named environment variable.

Stores: Knowledge blocks in a shared MongoDB collection. Use the registry's upsert/delete methods from application code to manage the source. Install the mongodb extra.

Search: By default, embeddings enable semantic retrieval and Atlas vector search where supported. Set embedding=None to use MongoDB text search.

MongoDB knowledge source
MongoDBKnowledgeRegistry(
    name="product_docs",
    description="Search product manuals.",
    uri_env="MONGODB_URI",
    database="max_ai",
    collection="knowledge",
)

Model providers#

CoreChatCompletionClient is the framework contract. A provider adapter maps typed messages, tool schemas, structured output, streaming chunks, and usage data to that provider's API and maps responses back. The reasoning loop depends on this contract, so it does not need provider-specific branches.

LocalOllamaLocal model server; configure model and host, with optional thinking and generation options. Useful for local development and deployments where the Ollama service is managed by you.
APIOpenAIOpenAI chat-completions client. Configure model and API-key environment variable; optional base URL, organization, project, and request options.
GatewayOpenRouterOpenAI-compatible routing through OpenRouter, with routing/fallback options and provider-specific settings.

The client carries a ModelConfig describing context window, output limit, tool calling, vision/audio, thinking, and tokenizer support. These are capability declarations consumed by runtime features such as compaction and multimodal message handling; choose values that match the actual model. Output is capped at 32K tokens across every client — room for a whole file in one tool call — and a reply cut at the limit is explained back to the model instead of silently dropped. Keep API keys in environment variables—serialized client config stores the variable name, not the secret.

OpenAI provider setup
from max_ai.capabilities.clients.openai import OpenAIChatCompletionClient
from max_ai.core.model.llm import ModelConfig

# Export OPENAI_API_KEY in the process environment before construction.
client = OpenAIChatCompletionClient(
    model="YOUR_PROVIDER_MODEL",
    api_key_env="OPENAI_API_KEY",
    config=ModelConfig(supports_function_calling=True),
)
# Pass client=client to Agent.
capabilities/clients/ollamacapabilities/clients/openaicapabilities/clients/openrouter
Provider configuration: what the client receives

Every provider client needs a provider-specific model. OpenAI accepts an API key or an api_key_env name plus optional base_url, organization, project, ModelConfig, and generation options. OpenRouter adds fallback models and routing preferences. Ollama accepts a host, optional API key, thinking settings, and keep-alive value.

ModelConfig declares runtime capabilities such as context window, output limit, tool calling, vision, audio, thinking, and token counting. Choose values that match the model; compaction and message handling rely on them. API credentials can be passed directly, but an environment variable name is safer and is what serialized configuration stores.

OpenAI client
OpenAIChatCompletionClient(
    model="YOUR_PROVIDER_MODEL",
    api_key_env="OPENAI_API_KEY",
    config=ModelConfig(supports_function_calling=True),
)

Reasoning · ReAct#

BaseReasoning is the loop contract and ReactLoop is the default. Each run binds its own strategy to the model client, tool dispatcher, middleware, and completion bus. Model requests, tool observations, guards, and final responses repeat until the turn closes or pauses. Explore the loop →

Reasoning configuration: loop settings and per-run inputs

ReactLoop constructor settings are max_loop_iterations (or None to follow the framework setting), max_connection_retries, and guards. The default guards retry schema errors, steer repeated calls, and check the run budget; pass an empty list to disable them.

When a run begins, the Agent binds a copy of the reasoning loop to that run's model client, tool dispatcher, middleware chain, compaction strategy, memory, and context limit. The loop method then receives messages and state through RunContext, the prepared prompt, streaming/cancellation settings, and any output schema.

Select a loop
reasoning = ReactLoop(
    max_loop_iterations=12,
    max_connection_retries=3,
)
agent = Agent(..., reasoning=reasoning)

Compaction#

There is no default: pass compaction=None (or omit it) and the window is never compacted, which is fine for short sessions. Use SlidingWindowCompaction to drop the oldest turns without an LLM call, or SummaryCompaction(threshold=0.8, keep_ratio=0.4) to summarize older turns with the model once the window is 80% full, keeping the summary in the prompt. Pass a strategy as compaction=...; it runs inside the loop before model calls. Its summary and counters live with the conversation RunContext; compaction reduces model context, not the need to persist the conversation.

SlidingWindowCompactionSummaryCompactionRunContext.compaction_state
Compaction configuration: token budget and strategy

Compaction is opt-in. The shared strategy settings include threshold (the fraction of the model window that triggers compaction), keep_ratio, min_keep_groups, tool-output truncation controls, and whether extracted older facts update memory.

SlidingWindowCompaction also receives max_turns and removes old turns without an LLM summary. SummaryCompaction receives summary_max_tokens and message_cap_tokens; it uses the model client to summarize older turns. Both return updated messages and state to the reasoning loop.

Choose a strategy
compaction = SummaryCompaction(
    threshold=0.8,
    keep_ratio=0.4,
    summary_max_tokens=2000,
)
agent = Agent(..., compaction=compaction)

Completion gates#

RuntimeCompletionGate is included in every Agent. It checks whether an answer is ready to close: open plans, declared Bash outputs, and unresolved failures can keep work in the loop. Pass additional CompletionBase implementations through gates=[...]. A gate's on_final_response(ctx) decision can accept, reject, or wait; observation hooks may record evidence but do not veto closure.

Configure built-in checks with RuntimeCompletionGate(RuntimeGateConfig(...)) in gates. See gate outcomes →

Middleware#

CoreMiddleware hooks surround the run (on_run_start, on_final_response, on_run_end, on_run_error), every model call (on_model_request, on_model_chunk, on_model_response, on_model_error), and every approved tool call (on_tool_request, on_tool_response). Raising StopRun(message) from a run or model hook ends the turn cleanly; a tool hook blocks a single call by returning a ToolResult instead. Pass middleware through middlewares=[...]; middleware observes and controls runtime behavior, while gates decide completion.

Budget and quotas

BudgetMiddleware enforces two kinds of limits at once: per-task caps (max_tokens, max_cost_usd, max_seconds) that stop a single run, and per-user quotas (quota=QuotaLimits(...)) that track daily and monthly spend across runs in a quota_store. LocalQuotaStore keeps counters on disk for a single process; MongoDBQuotaStore shares them across servers.

Per-task limits and a daily quota
from max_ai.capabilities.middleware import BudgetMiddleware
from max_ai.capabilities.quota_store import LocalQuotaStore
from max_ai.core.model.quota import QuotaLimits

budget = BudgetMiddleware(
    max_tokens=200_000, max_cost_usd=2.0, max_seconds=120,
    quota=QuotaLimits(daily_cost_usd=20.0, monthly_cost_usd=300.0),
    quota_store=LocalQuotaStore(base_path="./agent-data"),
)
agent = Agent(..., middlewares=[budget])

Tracing

TracingMiddleware() emits OpenTelemetry spans for runs, model calls, and tool calls. Call configure_langfuse() once at startup to send those spans to a Langfuse instance — docker-infra/ ships a local one for development.

Middleware configuration: hooks and their inputs

Each hook receives a MiddlewareContext (the current run, agent name, event emitter, and per-run state) plus the object for that lifecycle point: a task, a ModelRequest, a model result/chunk, or a ToolRequest/ToolResult.

Run and model hooks can observe or change requests and responses. Returning a ToolResult from on_tool_request supplies the tool result without executing the tool. Use middlewares=[...] on Agent. BudgetMiddleware receives per-run token/cost/time/call limits and optional quota/store settings; TracingMiddleware receives content-capture settings and an optional tracer provider.

Attach a middleware
budget = BudgetMiddleware(
    max_tokens=100_000,
    max_seconds=90,
)
agent = Agent(..., middlewares=[budget])
