Prompt layers

Prompt layers turn agent configuration and optional registry data into model instructions. They are rendered for each run, then adapted to the selected provider's message format.

The prompt stack#

max_ai.agents.Agent._build_prompt_stack() creates the prompt layers in this order. Policy, task analysis, rendering, and session state are always present. Skills, knowledge, and memory layers appear only when their matching registries are passed to the agent.

01

AgentPolicyLayer

Agent identity, description, developer instructions, and behavior policy.

Always · agent fields
02

TaskAnalysisLayer

Static guidance for interpreting the task, checking missing information, and deciding whether to plan or clarify.

Always · static template
03

RenderingLayer

Static response-format guidance for readable text, code, lists, links, and diagrams.

Always · static template
04

SkillsLayer

Renders available skill names and summaries after the skill registry is prepared. Full instructions stay in the materialized skill package.

When skills is set
05

KnowledgeLayer

Lets the model know which retrieval tools exist. Search results arrive later as tool-result messages.

When knowledge is set
06

MemoryLayer

Adds the current memory snapshot and describes available memory operations.

When memory is set
07

SessionStateLayer

Keeps the current plan and any compaction summary in the prompt so they survive transcript compaction.

Always · run state

Variable sources#

The agent collects values before rendering. A layer only reads the names used by its own template; it does not query a registry directly.

AgentPolicyLayername, description, instructionsAgent constructor
SkillsLayerloaded_skillsskills.get_skills() during prepare

MemoryLayerpersistent_memories, memory_toolsScoped memory registry

Not part of the prompt layers

The user task and chat history are CoreMessage entries in RunContext. Tool schemas are sent as the separate tools argument to the model client. Knowledge results are added as tool-result messages after retrieval.

Rendering a variable#

The template declares where a value belongs. At run time CoreLayer.render() inserts values into that position and returns a string. For example, AgentPolicyLayer has this structure:

Jinja2 template 
<identity>
  <name>{{ name }}</name>
  <description>{{ description }}</description>
  <instructions>{{ instructions }}</instructions>
</identity>
Agent values
render into
the placeholders ↓
Rendered layer text 
<identity>
  <name>math-assistant</name>
  <description>Answers questions with a calculator.</description>
  <instructions>Use the multiply tool when needed.</instructions>
</identity>

Templates use Jinja2. `CoreLayer` validates required and optional placeholders when it is constructed; strict rendering surfaces missing values instead of silently producing incomplete instructions.

Model client injection#

The agent packages the ordered stack and its rendered strings in PromptCtx. The reasoning loop passes it into the client on every model call. The provider adapter decides how to form the actual request.

Agent._prompts() and BaseReasoning._call_llm() 
variables = await self._prompt_variables(ctx)
prompts = PromptCtx(
    stack=self._stack,
    variables=variables,
    rendered_layers={
        type(layer): layer.render(variables)
        for layer in self._stack
    },
)

# ReactLoop supplies prompt context and tool schemas separately.
result = await self.client.run(
    ctx=self._model_context(ctx, transient_messages),
    prompts=prompts,
    tools=tools,
)

For Ollama, non-empty rendered layers are joined with blank lines into a system message. Conversation history and the current task follow as messages. Other model clients can assemble those pieces differently to match their provider APIs.

Create a custom layer#

Subclass CoreLayer to define a Jinja2 template, its required run variables, and optional static extra_variables. Give a serializable layer a StackConfig schema and a stable importable provider path. The Agent supplies name, description, and instructions as run variables.

Contract shape · abbreviated
class OrganizationRulesLayer(Component[StackConfig], CoreLayer):
    component_schema = StackConfig
    component_type = "prompts"
    def _default_template(self) -> str:
        return "Organization: {{ organization_name }}; agent: {{ name }}"
    def _required_variables(self) -> set[str]:
        return {"name"}

agent = Agent(..., prompt_layers=[OrganizationRulesLayer(
    extra_variables={"organization_name": "Acme"})])

CoreLayer uses Jinja2 StrictUndefined, so every template variable must be supplied. Keep the class in an importable module; when deserializing a trusted custom provider, allow its package prefix with allow_providers(...). See the custom prompt layer example →
